# AI 私厨管家设计文档

日期：2026-11-11  
状态：待用户批准

## 1. 意图与背景

构建一个可实际运行的 AI 私厨管家 Web 应用。用户上传冰箱或厨房中的食材图片，也可以补充文字要求；系统使用 LangChain 编排阿里云百炼 `qwen3.7-plus`，识别食材并推荐可制作的菜谱。产品重点是让用户从“我有什么”快速走到“今天做什么、怎么做”，而不是只返回一段泛化的聊天文本。

## 2. 目标

- 支持 JPG、PNG、WebP 食材图片上传与预览。
- 通过 `qwen3.7-plus` 原生视觉能力识别图片中的食材，返回结构化食材列表、置信说明和可能需要用户确认的项目。
- 结合识别结果、人数、口味、忌口、烹饪时间和难度偏好推荐菜谱。
- 以营养匹配、食材利用率、制作难度和耗时为维度计算可解释的排序分数。
- 有 Tavily API Key 时，通过 LangChain Tool 搜索公开菜谱或烹饪资料；没有 Key 时仍能使用模型生成菜谱。
- 找不到完全匹配菜谱时，提供替换食材和创意搭配建议。
- 支持基于本次识别和推荐结果的连续对话。
- 前端提供清晰的食材确认、菜谱卡片、排序筛选、步骤与聊天体验。
- 提供 README、环境变量模板、启动说明和基础自动化测试。

## 3. 非目标

- 首版不提供用户注册、云端账号体系、支付或订阅。
- 首版不做库存长期管理、采购下单、外卖或智能厨电控制。
- 首版不把模型生成结果视为医疗营养建议，不计算临床级营养数据。
- 首版不提供后台运营系统、多人协作或公开菜谱社区。
- 首版不做生产环境云部署，只保证本地开发与可部署结构。

## 4. 反目标

- 不把 API Key 写入源码、前端包、日志或版本控制。
- 不伪造真实搜索来源；无 Tavily 时必须清楚标记为 AI 生成建议。
- 不让模型自由输出无法验证的任意 JSON；核心结果使用 Pydantic/LangChain 结构化输出验证。
- 不仅做一个聊天框。核心任务必须通过结构化 UI 完成。
- 不因模型或搜索失败而让整个页面白屏；错误应可恢复并提供重试。

## 5. 已确定方案与备选方案

### 方案 A：FastAPI + LangChain Python + React/Vite（已选择）

前后端分离。Python 侧适合 LangChain、Pydantic 和工具编排，React 侧适合完成上传、卡片和流式聊天等产品化界面。代价是需要分别运行前后端。

### 方案 B：Streamlit + LangChain Python

开发和演示最快，但界面定制、响应式体验、复杂交互和后续扩展能力较弱，因此未选。

### 方案 C：Next.js + LangChain.js

单项目交付方便，但偏离已选择的 Python LangChain 技术路线，工具与数据校验实现也需要转向 TypeScript，因此未选。

## 6. 约束与已验证事实

- 项目目录 `D:\\cookagent` 当前为空，且不是 Git 仓库，需要从零初始化。
- 模型固定为 `qwen3.7-plus`。
- 通过阿里云百炼北京地域、工作空间专属 OpenAI 兼容地址调用。
- 官方文档确认 `qwen3.7-plus` 支持文本、图片、结构化输出与 Function Calling。
- 本地图片采用 Base64 Data URI 发给模型；后端限制单张原始图片最大 10 MB，低于官方 20 MB 上限以控制延迟和内存。
- 用户提供的 CSV 只作为本地凭据来源。应用运行时读取 `.env` 或环境变量，不复制密钥到仓库。
- Tavily 是可选集成；没有 Tavily Key 时核心功能仍可使用。
- 前端和 API 默认使用中文。
- 首版每次分析恰好接收一张图片；用户可重新分析新图片，不在同一会话追加图片。

## 8. LangChain 工作流

系统采用明确的有向业务流程，不使用无限自主循环的 Agent：

1. **输入规范化**：验证图片类型和大小，整理人数、口味、忌口、时长与难度。
2. **视觉识别链**：把图片和严格提示词发送给 `qwen3.7-plus`，通过结构化输出得到食材、估算数量、置信度和待确认项。
3. **食材确认**：前端允许用户增删改识别结果，确认后再生成推荐，避免错误识别一路传播。
4. **候选检索工具**：配置 Tavily 时，用确认后的食材和约束构造中文搜索词，获取少量候选来源；未配置时跳过。
5. **菜谱生成链**：模型结合已确认食材、用户约束和可选搜索摘要，生成结构化菜谱候选。
6. **确定性排序服务**：后端根据模型返回的基础字段计算统一分数，避免把排序完全交给模型。
7. **对话链**：保留当前会话的食材、菜谱与最近消息；回答替换食材、步骤解释和调整份量等问题。

### 排序建议

总分 100：食材覆盖率 35、偏好符合度 25、营养均衡 20、时间/难度匹配 15、来源完整度 5。过敏原不参与加权评分，而是在生成前和返回前执行绝对排除。营养均衡采用可解释的食物组启发式（蛋白质、蔬果、主食与烹调方式），不宣称精确营养数值。前端展示总分和最关键的两个理由。用户可切换“综合、最快、最简单、食材利用最高”等排序方式。

## 9. 核心数据结构

- `Ingredient`：名称、标准化名称、估算数量、单位、置信度、来源（图片/用户）。
- `UserPreferences`：人数、口味、过敏原、普通忌口、最大用时、难度；过敏原和普通不喜欢的食物分开保存。
- `Recipe`：标题、简介、份量、用时、难度、所需/缺少食材、步骤、营养摘要、标签、评分明细、来源链接、来源类型。
- `ConversationMessage`：角色、内容、时间。
- `SessionContext`：会话 ID、已确认食材、偏好、菜谱、消息。

所有模型输出先通过 Pydantic 验证；验证失败时只进行一次带错误反馈的重试，再返回可理解的错误。

## 10. API 设计

- `GET /api/health`：服务和配置状态，不返回敏感值。
- `POST /api/ingredients/analyze`：multipart 图片 + 可选文字，返回会话 ID 与识别结果。
- `POST /api/recipes/recommend`：会话 ID、确认后的食材与偏好，返回排序后的菜谱列表。
- `POST /api/chat`：会话 ID、消息，首版返回完整回答；若实现稳定则采用 SSE 流式返回。
- `GET /api/sessions/{session_id}`：恢复当前会话状态。
- `DELETE /api/sessions/{session_id}`：清除本地会话。

统一错误格式：`code`、`message`、`retryable`、可选 `details`。生产模式不返回堆栈或上游响应正文。

首版聊天只提供上下文回答，不自动修改已确认食材、偏好或菜谱卡片。需要变更份量或替换食材时，回答给出建议，用户重新提交推荐表单后才更新结构化状态。

## 11. 前端体验

### 页面结构

- 顶部：品牌“灶边 AI / 私厨管家”、模型在线状态和新建会话按钮。
- 左侧主区：图片拖拽上传、图片预览、食材识别结果编辑、用餐偏好表单。
- 右侧结果区：首次进入时显示使用引导；识别后显示食材；推荐后显示菜谱卡片与筛选排序。
- 底部或右侧抽屉：上下文聊天，支持询问替代食材、步骤和份量。
- 移动端改为单列步骤式布局。

### 视觉风格（实现者默认决定，可由用户调整）

采用温暖、干净的现代厨房风格：米白背景、番茄红/香草绿点缀、深灰正文、柔和卡片阴影。避免套用通用后台仪表盘样式。交互状态包含空态、上传中、识别中、搜索中、生成中、失败与重试。

### 主流程

上传图片 → 识别食材 → 用户确认/修正 → 填写偏好 → 获取推荐 → 查看菜谱详情 → 继续追问。

## 12. 安全与隐私

- 模型 Key、OpenAI 兼容地址和 Tavily Key 分别从 `.env` 中的 `DASHSCOPE_API_KEY`、`MODEL_BASE_URL`、`TAVILY_API_KEY` 加载；应用启动时显式调用 `load_dotenv()`，随后再由 Settings 读取。
- 本地 `.env` 保存实际密钥并加入 `.gitignore`；`.env.example` 仅保留变量名、模型名 `qwen3.7-plus` 和安全占位符，不包含任何真实密钥。
- 用户 CSV、上传图片和运行日志均不持久化或加入忽略规则。
- CORS 默认只允许本地 Vite 地址，并可通过环境变量覆盖。
- 上传文件校验 MIME、扩展名、大小和图片解码结果。
- 不将上游请求头、密钥或完整 Base64 图片写入日志。
- 食物过敏提示明确声明：模型建议不能替代标签核验或专业医疗意见。

## 13. 降级与异常处理

- 未配置模型 Key：健康检查返回未配置，前端展示配置指引；不伪造识别结果。
- Tavily 未配置或失败：继续使用模型推荐，并将来源标记为“AI 生成”。
- Tavily 可用时，每个引用网络信息的菜谱必须返回实际使用的来源标题和 URL，并标记为“AI 综合网络资料”；没有直接来源的菜谱仍标记为“AI 生成”，不得挂靠无关链接。
- 图片无法识别：返回可编辑的空食材表，并提示用户手工添加。
- 模型结构化输出失败：重试一次；仍失败则返回可重试错误。
- 会话不存在：提示新建会话或重新分析图片。

### 验收场景

1. 上传一张包含 3 种以上食材的图片，页面显示可编辑的结构化识别结果。
2. 设置人数、忌口、时间与难度后，至少返回 3 个有排序理由的菜谱。
3. 菜谱详情包含用料、缺少食材、步骤、时间、难度和营养摘要。

6. API Key 不出现在前端构建产物、日志、Git 追踪文件或错误响应中。

## 15. 实现者可自行决定的事项

- 具体组件拆分、CSS 命名、图标库和轻量动画实现。

- 菜谱卡片默认每次返回 4 个候选，允许在配置中调整。

## 16. 独立实现审阅后的决策

- **过敏与普通忌口**：分开输入；过敏原是绝对排除条件，推荐结果不得仅因综合评分高而绕过。
- **营养评分**：首版使用食物组和烹调方式启发式，不引入未经验证的精确营养数据库或医疗目标。
- **图片数量**：首版一次一张，避免多图合并、去重和追加状态增加不必要复杂度。
- **搜索出处**：逐条保留实际引用来源；模型合成内容与直接来源清楚区分。
- **聊天修改状态**：首版为信息型，不自动变更结构化会话状态，避免隐式修改导致界面与后端不一致。
- **本地配置加载**：按用户要求把模型 API、兼容地址和 Tavily API 放入 `.env`，通过 `load_dotenv()` 加载；真实值不进入设计稿和版本控制。
